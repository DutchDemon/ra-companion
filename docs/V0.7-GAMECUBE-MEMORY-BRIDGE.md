# v0.7 GameCube memory bridge validation

Status: implementation/diagnostic gate. This phase does **not** make local rcheevos state authoritative and does not submit RetroAchievements activity.

The validation build is stamped `0.7.0-dev.2` so it cannot be confused with the stable `0.6.4` release. The packaged build must pass TypeScript typechecking, the full regression suite, the packaged `RAM_DIAGNOSTICS.bat -SelfTest`, Microsoft Defender, and ClamAV before it is offered for real Dolphin parity testing.

## Proven GameCube address model

The pinned rcheevos v12.5.0 source (`1433173220a7eaede6a9ed7a18e94117be1821e0`) defines GameCube memory as a single region:

```c
{ 0x00000000U, 0x017FFFFFU, 0x80000000U, RC_MEMORY_TYPE_SYSTEM_RAM, "System RAM" }
```

Therefore:

- RA logical address `0x00000000` = GameCube guest `0x80000000`
- RA logical address `0x017FFFFF` = GameCube guest `0x817FFFFF`
- GameCube MEM1 size = `0x01800000` (24 MiB)

Modern Dolphin's `dolphin-emu.<PID>` shared-memory mapping exposes MEM1 at shared offset zero. The existing, already validated PowerShell reader uses `guestAddress - 0x80000000` for the shared-memory offset. For GameCube, this means the rcheevos logical address and Dolphin shared-memory offset are numerically identical.

Example used by the Twilight Princess validation fixture:

```text
RA logical 0x0040AFC0
      = guest 0x8040AFC0
      = Dolphin shared-memory offset 0x0040AFC0
```

## Native bridge contract

`ra-runtime-helper.exe` may open only these mappings:

- `dolphin-emu.<PID>`
- `Local\dolphin-emu.<PID>`

The mapping must be opened with `FILE_MAP_READ`. The helper must not use `FILE_MAP_WRITE`, `WriteProcessMemory`, process injection, or any other memory-writing mechanism.

The first diagnostic protocol exposes:

- `attachDolphin` — attach read-only to a known Dolphin PID
- `detachDolphin` — release the mapping
- `memoryStatus` — report mapping, PID, GameCube header and address model
- `readMemory` — bounded diagnostic read from an RA logical GameCube address

These commands are diagnostics only. They do not call `rc_runtime_do_frame` yet and cannot change official achievement state.

`RAM_DIAGNOSTICS.bat` compares the native bridge with the existing PowerShell reader. Twilight Princess USA (`GZ2E01`) is the first real-machine parity fixture.

## rcheevos raw achievement definitions

The pinned rcheevos RAPI interface provides `rc_api_fetch_game_data_request_t`. Its response contains the raw achievement `definition` strings intended for `rc_runtime_activate_achievement`, plus the game's Rich Presence script, achievement type and leaderboard definitions.

The pinned rcheevos tests show the request contract as:

```text
POST https://retroachievements.org/dorequest.php
r=patch&u=<username>&t=<connect-token>&g=<game-id>
```

RA Companion must use that official definition flow instead of attempting to reconstruct achievement conditions from the public Web API.

## Authentication boundary

The existing RA Companion account connection uses the public Web API key for endpoints such as `API_GetGameInfoAndUserProgress.php`. It must **not** be silently reused as the rcheevos connect token.

Current RAWeb `login2` authenticates either:

- username + password, returning a `connect_token`, or
- username + an existing `connect_token`.

The future runtime credential flow therefore remains separate:

1. Keep the existing Web API key for authoritative public progress/library calls.
2. If runtime definitions require authentication, perform a one-time `login2` password exchange.
3. Never persist the password.
4. Store only the returned connect token, protected with Electron `safeStorage` when available.
5. Provide a clear disconnect/re-authentication path for expired/revoked connect tokens.
6. Do not start a RetroAchievements gameplay session, send pings, award achievements, or submit leaderboard entries from RA Companion.

This credential flow is deliberately **not implemented in the memory-bridge phase**. It will be a separate reviewed step after real Dolphin memory parity is proven.

## Authority rule

Always preserve this split:

- RetroAchievements server: authoritative `Completed` / `Locked`
- local rcheevos runtime: observer-only live state (`Active`, `Primed`, measured progress, local trigger context)

A local `TRIGGERED` event must never be presented as an official unlock unless server progress later confirms it.
