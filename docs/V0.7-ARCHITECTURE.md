# RA Companion v0.7 Architecture Plan

Status: **design/audit only**  
Branch: `refactor/v0.7.0-architecture`  
Baseline to preserve: **v0.6.4**

This document defines the cleanup and multi-game architecture for RA Companion before implementation starts. The primary goal is to turn the current Twilight Princess-focused application into a maintainable, game-agnostic companion while preserving the proven read-only Dolphin integration, official RetroAchievements progress authority, overlay behavior, updater, account isolation, and v0.6.4 Windows branding.

## 1. Core decisions

1. **Official RetroAchievements server progress remains authoritative.** Local RAM/runtime state may enrich the UI, but it must never turn a locked achievement into an officially completed achievement.
2. **The Dolphin memory integration stays read-only.** RA Companion must never write emulator memory.
3. **rcheevos is an observer/evaluator, not an achievement submission client.** RA Companion must not submit unlocks, leaderboard entries, or duplicate the emulator's RetroAchievements session.
4. **No guessed counters or missability.** Measured progress must come from rcheevos/official RA data or a validated per-game profile. Missable deadlines/instructions come from official RA type metadata plus curated guide/profile metadata.
5. **Game-specific code must not live in generic UI or Electron bootstrap files.** Twilight Princess becomes one profile plugged into generic services.
6. **The existing patch-stack build system is temporary technical debt.** v0.7 starts by promoting the exact working v0.6.4 result to canonical source before structural refactoring.

## 2. Current-state audit

The repository currently reconstructs an old source archive and applies a long sequence of PowerShell transformations during CI. This has been useful for safe incremental releases, but it is now an obstacle to a larger refactor because the readable override files are not necessarily identical to the final v0.6.4 files that users run.

The current build path is roughly:

```text
build-source/part*.b64
        |
        v
verified legacy source archive
        |
        +--> build-overrides/src/*
        +--> build-overrides/electron/*
        |
        v
apply-v0.4.5 ... apply-v0.6.4
        |
        v
actual v0.6.4 application source
        |
        v
Vite + Electron Builder + NSIS
```

The main architectural hotspots are:

- `electron/main.cjs`: updater, configuration, safeStorage, overlay lifecycle, Dolphin process detection, RAM helper process, RA API calls, caches, snapshot assembly, windows, IPC, and shortcuts are mixed together.
- `src/main.tsx`: generic achievement UI, overlay UI, live state hooks, and Twilight Princess-specific logic are mixed together.
- `src/profiles/twilightPrincess.ts`: useful game-specific context logic exists, but the renderer imports it directly instead of through a profile interface.
- `src/profiles/twilightPrincessGuide.ts`: curated guide metadata is already separated and should remain a profile-level concern.
- Historical build transforms and old workflows remain in the repository and should stop being part of the active build after source promotion is proven.

## 3. Target architecture

The target data flow is:

```text
                         RetroAchievements
                         +---------------+
                         | Public API    |
                         | official      |
                         | user progress |
                         +-------+-------+
                                 |
                                 v
+------------+          +--------+---------+          +------------------+
| Dolphin    |          | Electron services |          | React renderer   |
|            |          |                  |          |                  |
| shared RAM +--------->| runtime-helper   +--------->| Achievements     |
| read-only  |          | bridge/state     |          | Overlay          |
+------------+          |                  |          | Settings         |
                        | RA API/library   |          +------------------+
                        +--------+---------+
                                 |
                                 v
                      +----------+-----------+
                      | ra-runtime-helper.exe |
                      |                      |
                      | Dolphin memory       |
                      | rcheevos / rhash     |
                      | rc_runtime           |
                      | Rich Presence        |
                      +----------------------+
```

The native helper is deliberately separated from Electron. This avoids Node/Electron native-addon ABI churn and gives the read-only runtime a small, auditable boundary.

## 4. Data authority model

Every field shown by RA Companion must have a defined authority.

| Data | Authority | Persistent? | May local runtime override it? |
| --- | --- | ---: | ---: |
| Official unlocked/completed state | RetroAchievements server progress | Yes | **No** |
| Hardcore completion count | RetroAchievements server progress | Yes | **No** |
| Achievement title/description/type | RA game data | Yes/cacheable | No, except presentation metadata |
| Active game | Validated detection/runtime identity | Session | N/A |
| Live trigger state | rcheevos runtime | Session only | N/A |
| Measured live progress | rcheevos when available, otherwise validated profile | Session | N/A |
| Rich Presence | rcheevos script or RA server fallback | Session | N/A |
| Missable instructions/deadline | Curated game profile/guide | Yes | N/A |
| Custom collectible/context counters | Validated game profile | Session | N/A |

A local `TRIGGERED` event is **not** an official unlock. The UI may use it for live context only until the official RA server progress reports the achievement as earned.

## 5. rcheevos integration

RA Companion will target an exact official rcheevos release, not a moving branch. At the time of this design, the current official release is **v12.5.0**, tag commit:

```text
1433173220a7eaede6a9ed7a18e94117be1821e0
```

The rcheevos README recommends integrating from the stable `master` release line rather than `develop`. The implementation should vendor or fetch an exact tag/commit with checksum verification and include the MIT license in third-party notices.

### 5.1 Preferred API level

The preferred design is **RAPI + `rc_runtime`**, not a full submission-capable `rc_client` session.

rcheevos exposes game patch data through `rc_api_fetch_game_data_request`. Its response includes:

- game ID and console ID
- title and image metadata
- raw Rich Presence script
- achievement definitions
- achievement type (`standard`, `missable`, `progression`, `win`)
- leaderboard definitions

The raw achievement `definition` can be activated in `rc_runtime`, which can then evaluate the achievement against our read-only memory callback and expose measured progress and runtime states.

This design intentionally does **not** implement award/submit endpoints.

### 5.2 Fallback option

If low-level RAPI integration proves unnecessarily costly, `rc_client` may be evaluated as a fallback **only in locked spectator mode enabled before game load**. Before adopting that route, automated network tests must prove that RA Companion does not start a gameplay session, submit unlocks, submit leaderboard entries, or emit periodic session pings.

### 5.3 Runtime sampling requirement

The current PowerShell RAM reader is useful for UI context but is not a sufficient long-term runtime clock for exact achievement evaluation. rcheevos expects frame-level evaluation. The native helper therefore needs a high-frequency/read-on-demand memory bridge capable of tracking the emulated frame cadence closely enough for rcheevos semantics.

Until that is implemented and validated, RA Companion must **not** advertise generic local trigger-state parity with the emulator.

## 6. Native helper boundary

Proposed executable:

```text
ra-runtime-helper.exe
```

Responsibilities:

- attach to supported Dolphin shared-memory mappings read-only
- expose bounded memory reads to rcheevos
- identify basic emulator/game state
- host `rc_runtime`
- activate achievement definitions and Rich Presence scripts
- expose measured values and runtime events
- optionally perform `rhash` identification when an accessible game file/reader is available
- emit structured JSON messages to Electron

Non-responsibilities:

- no achievement unlock submission
- no leaderboard submission
- no save-state manipulation
- no Dolphin process injection
- no memory writes
- no renderer/UI code
- no long-term official completion state

Suggested JSON protocol envelope:

```json
{
  "protocol": 1,
  "type": "runtime-state",
  "timestamp": 0,
  "game": {
    "consoleId": 16,
    "gameId": 0,
    "gameCode": "",
    "hash": null
  },
  "richPresence": "",
  "achievements": []
}
```

The protocol must be versioned before the helper is used by a release build.

## 7. Game identification strategy

Game identification has to distinguish convenience detection from authoritative identity.

### Tier A — session hint

Dolphin process/window state and game code can identify that a supported title is probably running. This is fast but is not sufficient to distinguish every region/revision/hash.

### Tier B — RA/session identity

Where RA/Dolphin state provides an exact active RA Game ID, that may be used as the live game identity after validation.

### Tier C — exact rcheevos hash

`rhash` is the preferred exact identity when RA Companion can access a compatible game image/file stream. GameCube hashing is implemented by rcheevos.

ISO/GCM file paths are a straightforward target. **RVZ must be treated as an open research item.** Do not assume rcheevos can hash RVZ directly. A Dolphin-aware/custom reader may be required.

The UI should know the identity confidence, for example:

```text
hint -> game-id -> exact-hash
```

Game-specific enhanced profiles may require a minimum confidence level.

## 8. Authentication and credentials

The current RA Companion stores the user's Web API key using OS-backed `safeStorage` where available. The rcheevos runtime endpoints use an RA runtime/login token flow and must be treated as a separate credential until compatibility is explicitly proven.

Rules:

- never store the user's RA password
- never silently repurpose credentials without verifying the server contract
- if a password-based token exchange is required, the password exists only for the duration of the login request
- store only the resulting token with `safeStorage`
- provide a clear disconnect/revoke path
- keep the existing Web API credential path for official public progress/library calls unless a later design safely replaces it

Authentication implementation is a separate reviewed step, not part of the first cleanup commit.

## 9. Game support tiers

RA Companion should describe support honestly rather than treating every game as equally enhanced.

### Tier 1 — Generic RA support

Available for any game we can identify and query:

- game title/art
- achievement set
- official account progress
- completed/locked state
- offline remembered achievement library
- normal filtering/grouping

### Tier 2 — Runtime-enhanced support

Available after the rcheevos memory bridge is validated for the game/platform:

- evaluated Rich Presence
- live measured progress where the achievement definition exposes it
- live runtime state where reliable
- generic live overlay context

### Tier 3 — Curated companion profile

Available only for games for which we have validated metadata:

- missable deadline/instructions
- context-sensitive warnings
- validated custom counters
- story/dungeon/route context beyond generic Rich Presence

Twilight Princess becomes the first Tier 3 profile and the validation fixture for Tier 2.

## 10. Renderer/profile boundary

The renderer must stop importing Twilight Princess internals directly.

Proposed profile contract (illustrative, not final API):

```ts
export interface GameProfile {
  key: string;
  name: string;
  raGameIds?: number[];
  gameCodes?: string[];
  enhance(input: GameProfileInput): GameEnhancement;
}
```

Suggested layout:

```text
src/
  app/
  components/
  pages/
  hooks/
  services/
  profiles/
    registry.ts
    twilight-princess/
      profile.ts
      guide.ts
      ram.ts
      tests/
```

Generic renderer code may consume `GameEnhancement`; it must not contain checks such as `GZ2E01`, Poe Soul names, Faron Tear fields, or Twilight Princess achievement titles.

The existing text-based TP counter fallbacks should move into the TP profile during cleanup. Where rcheevos later provides an authoritative measured value, prefer the runtime value and retire the heuristic.

## 11. Electron service split

`electron/main.cjs` should become bootstrap-only. Proposed boundaries:

```text
electron/
  main.cjs
  ipc/
    config.cjs
    overlay.cjs
    runtime.cjs
    library.cjs
    updates.cjs
  services/
    config-service.cjs
    update-service.cjs
    ra-api-service.cjs
    achievement-library-service.cjs
    dolphin-service.cjs
    runtime-helper-service.cjs
  windows/
    main-window.cjs
    overlay-window.cjs
```

Do not combine this refactor with a CommonJS-to-TypeScript migration. First establish clean boundaries with minimal behavior change; language/tooling changes can happen later if they provide a clear benefit.

## 12. Source promotion: first implementation phase

Before moving functions around, create one canonical source tree representing the exact v0.6.4 application after all historical transforms have run.

Procedure:

1. Reconstruct v0.6.4 using the current trusted pipeline.
2. Capture the resulting application source as canonical source in the repository.
3. Build the canonical source directly without replaying the historical patch chain.
4. Run the complete regression suite, production build, NSIS packaging, packaged EXE icon check, Defender, and ClamAV.
5. Compare critical behavior with v0.6.4: updater, account config, offline library, overlay, hotkeys, Dolphin RAM state, TP contextual missables, and Windows branding.
6. Only after parity passes, retire historical transforms from the active build path. Keep history through git/archive rather than executing it on every future release.
7. Update the README so it describes the real architecture and current release pipeline.

This source promotion should contain **no deliberate product behavior changes**.

## 13. Refactor implementation sequence

After source promotion:

### Phase 1 — Electron boundaries

Split configuration, updater, RA API, achievement library, Dolphin detection, runtime-helper bridge, overlay window, and IPC into modules. Preserve all existing external behavior.

### Phase 2 — Renderer boundaries

Split the monolithic renderer into app shell, pages, achievement components, overlay components, hooks, and service/types modules. Preserve UI/behavior.

### Phase 3 — Profile registry

Move all Twilight Princess assumptions behind a generic profile registry. TP should still behave exactly like v0.6.4.

### Phase 4 — Native helper proof of concept

Build and package a minimal `ra-runtime-helper.exe` with pinned rcheevos. First milestones:

- process starts/stops cleanly with Electron
- versioned JSON protocol works
- Dolphin shared memory can be read without writes
- helper remains stable at required sampling frequency
- no user-facing runtime claims yet

### Phase 5 — rcheevos runtime validation on Twilight Princess

Use TP as the comparison fixture:

- fetch raw game definitions/Rich Presence through the approved runtime API flow
- activate the Rich Presence script locally
- activate a small test set of achievement definitions
- compare measured values and state transitions against expected emulator/game behavior
- validate performance and CPU usage

### Phase 6 — generic GameCube rollout

Once TP validates the generic runtime path, enable Tier 1/2 support for additional GameCube games without adding game-specific code to generic components.

## 14. Validation gates

No phase moves forward merely because it compiles.

Required gates include:

- existing v0.6.4 regression tests remain green
- new module-boundary tests are added as code moves
- official server progress remains the only source of completed/locked state
- account isolation remains intact
- offline achievement library remains available
- updater still installs/restarts correctly
- overlay movement/resize/theme/taskbar behavior remains unchanged
- packaged Windows RA icon remains correct
- Dolphin/RA Hardcore remains active during read-only observation
- native helper performs no process injection or memory writes
- rcheevos runtime network layer contains no award/submit endpoints
- if `rc_client` is ever used, tests prove locked spectator mode and absence of session/unlock/leaderboard submission traffic
- measured counters must have a traceable source (`rcheevos` or validated profile)
- RVZ/hash support is not claimed until tested

## 15. Explicit non-goals for the cleanup

The cleanup phase will not:

- redesign the UI again
- change the established charcoal/orange RA theme
- add speculative support for every console at once
- auto-generate missable guidance from achievement conditions
- remove the existing TP curated guide data
- turn RA Companion into an emulator or official RA client
- submit achievements on the user's behalf

## 16. Open research items

These must be answered by small isolated spikes before production integration:

1. What is the cleanest supported credential/token flow for fetching rcheevos runtime patch data from a third-party observer application?
2. Can the native helper obtain a sufficiently accurate emulated-frame cadence from modern Dolphin shared memory/process state, or do we need a different synchronization strategy?
3. What exact GameCube address translation is required between RA definitions and Dolphin's exposed MEM1/MEM2 layout for all supported revisions?
4. Can exact RA hashing be performed for RVZ without converting the image, and if so through which documented/custom file-reader path?
5. Can the active RA Game ID be obtained reliably enough from Dolphin/RA state to avoid hashing for normal live operation while still using hashing for verification?
6. Which rcheevos runtime events are useful to expose in the overlay without accidentally implying an official unlock?

## 17. Definition of success for v0.7 architecture work

The architecture work is successful when:

- RA Companion builds from a clean canonical source tree.
- Generic Electron and renderer code contain no Twilight Princess assumptions.
- Twilight Princess still has all v0.6.4 behavior through a profile.
- The app has a stable helper protocol boundary ready for rcheevos.
- A pinned, licensed rcheevos build can run read-only against Dolphin memory.
- Official RA server progress remains authoritative.
- Adding the next GameCube title does not require editing the main Electron bootstrap or main renderer component.

Only after those conditions are met should we start calling the application broadly multi-game runtime-enhanced.
